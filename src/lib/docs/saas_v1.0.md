# التحليل المعماري وهيكل البيانات - نظام "جيماوي" SaaS v1.0

بناءً على الشاشات السبعة (بلوكات السوبر أدمن) التي تم تصميمها، هذا هو التحليل الشامل للعلاقات وهندسة قاعدة البيانات المقترحة.

---

## 1. تحليل العلاقات بين الشاشات (Screen Interdependencies)

النظام مصمم كمركز قيادة مركزي (Hub) يتحكم في مئات المستأجرين (Gyms). العلاقات كالتالي:

*   **دليل الجيمات (Tenants Directory) ↔ مصفوفة التحكم (Feature Matrix):**
    *   كل سجل في الدليل يفتح "مصفوفة التحكم" الخاصة به. تفعيل ميزة (مثل الـ HR) في المصفوفة يغير صلاحيات الوصول للمستأجر فوراً.
*   **بوابة الدعم (Support Tickets) ↔ دليل الجيمات:**
    *   كل تذكرة دعم مرتبطة بـ `TenantID`. الضغط على التذكرة يتيح للسوبر أدمن الانتقال لملف الجيم أو استخدام "Ghost Mode" للتحقق من المشكلة.
*   **الإدارة المالية (SaaS Billing) ↔ دليل الجيمات:**
    *   الفواتير تُولد بناءً على "الباقة" المختارة في دليل الجيمات. انتهاء الفاتورة دون دفع يؤدي لتجميد حالة الجيم في الدليل آلياً.
*   **محرك البث (Broadcast) ↔ كافة الشاشات:**
    *   يعمل كقناة تواصل عرضية (Cross-cutting) لإبلاغ جميع المستأجرين النشطين في الدليل بأي تحديثات.
*   **الأمن والنسخ الاحتياطي ↔ سجل الرقابة (Audit Logs):**
    *   أي محاولة "غش" مرصودة تظهر كتنبيه أمني وتُسجل كحدث (Event) في سجل الرقابة للرجوع القانوني.

---

## 2. هيكل قاعدة البيانات المقترح (Multi-tenancy Architecture)

لضمان عزل البيانات (Data Isolation) والأداء العالي، نقترح نموذج **"Schema-per-Tenant"** أو **"Shared Schema with Discriminator"** حسب حجم البيانات، ولكن للـ SaaS v1.0، النموذج الأنسب هو الهجين:

### أ) جداول النظام الأساسي (Central/SaaS Schema)
هذه الجداول يراها السوبر أدمن فقط وتدير المنصة ككل:

*   **`Tenants` (الجيمات):**
    *   `id` (UUID), `name`, `subdomain`, `custom_domain`, `logo_url`, `status` (active/suspended), `plan_id`.
*   **`SubscriptionPlans` (الباقات):**
    *   `id`, `name`, `price`, `max_members`, `features_json` (تخزين المميزات المفعلة للمصفوفة).
*   **`SuperAdminUsers`:** بيانات دخول السوبر أدمن.
*   **`SupportTickets`:** `id`, `tenant_id`, `subject`, `priority`, `status`, `created_at`.
*   **`AuditLogs`:** `id`, `tenant_id`, `action_type`, `ip_address`, `timestamp`.

### ب) جداول المستأجرين (Tenant-Specific Data)
يتم فلترة هذه الجداول دائماً بـ `tenant_id`:

*   **`Members`:** بيانات المشتركين داخل كل جيم.
*   **`Staff`:** الموظفين والرواتب الخاصة بكل جيم.
*   **`Payments`:** الفواتير الداخلية للجيم مع عملائه.
*   **`BodyMetrics`:** قياسات الجسم الخاصة بالمشتركين.

---

## 3. استراتيجية العزل والأمن (Isolation Strategy)

1.  **Row-Level Security (RLS):** تفعيل RLS على مستوى قاعدة البيانات (مثل PostgreSQL) لضمان أن أي استعلام لا يمكنه جلب بيانات لا تخص `TenantID` الحالي.
2.  **Ghost Mode Security:** عند دخول السوبر أدمن بالنيابة عن مدير الجيم، يتم إنشاء "Short-lived Session Token" بصلاحيات محدودة جداً وتُسجل كافة حركاته في الـ Audit Logs تحت وسم "SuperAdmin Impersonation".
3.  **Scalability:** عزل ملفات الميديا (اللوجوهات) في S3 Buckets مقسمة بـ `tenant_id` لسرعة الاستدعاء.

---

## 4. مسار البيانات (Data Flow)

1.  **الإنشاء:** السوبر أدمن يضغط "إنشاء جيم" ← يتم إضافة سجل في `Tenants` ← يتم تشغيل `Database Migrator` لتهيئة جداول الجيم الجديد ← يتم إرسال إيميل ترحيبي.
2.  **التحكم:** تغيير الـ Toggle في مصفوفة المميزات ← تحديث `features_json` في جدول المستأجر ← الواجهة البرمجية (API) تقرأ التحديث وتخفي/تظهر الموديولات فوراً.
